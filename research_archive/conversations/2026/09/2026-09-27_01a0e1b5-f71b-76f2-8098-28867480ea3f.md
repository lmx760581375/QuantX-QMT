## 我认为真正的突破口

核心方向应该从“分钟数据独立预测全市场收益”改成：

针对日线 Reward Top50 或弱转强候选，预测：

- 收盘至次日开盘收益；
- 次日是否跳空低开；
- 买入后 1–2 日最大不利波动；

- 尾盘强势究竟是持续买盘还是冲高回落。

这比让分钟模型重新学习 H7/H15 全市场排序更符合分钟数据的信息尺度。


这样分钟模型回答的是：

> 两只日线质量相近的股票，哪一只当前分钟状态更好？

- 否决明显差的入场；

- 调整买入时点；
- 不改变 H15 主持有逻辑。

> 对于日线模型认为质量接近的候选，分钟状态能否判断谁更好？

### 1. 日线模型完全冻结

保留现有流程：

```text
日线 Reward
→ Return Top50
→ 风险重排
→ 得到完整日线排名
```

分钟模型不参与全市场筛选，也不改变日线模型。

不要像上次一样全市场训练。

```text
同一天

```

例如只比较：

- rank 距离不超过 5；
- 或日线 score percentile 差不超过 5%。

- 最后 1/3/6/12 根收益；
- 最后一小时相对全天走势；
- 收盘位置、VWAP 偏离；
- 尾盘成交额和成交量的时段残差；
- 个股相对市场、行业的分钟强弱；
- 冲高回落、尾盘加速；
- 涨停距离、价格跳变风险；
- 横截面异常成交额排名。

已有分钟设计中已经包含时段量能残差等基础字段，可直接复用：[分钟 AE 设计](${HOME}/git/quantization/quantx/docs/development/19_MINUTE_AE_REWARD_BASELINE_DESIGN.md)。

## 三种比较关系分别学什么

### 1. 同日、不同股票

这是当前 baseline：

```text
A、B 属于同一个 signal_date
rH(A) > rH(B) + margin
→ score_cs(A) > score_cs(B)
```

它学习横截面选股能力。优点是同一天的大盘涨跌、流动性环境基本被抵消；缺点是只知道“当天谁更好”，不保证分数跨日期可比。

### 2. 同一股票、不同时间

这是你最有价值的新想法：

```text
同一股票 i
状态 T1 的未来表现优于状态 T2
→ score_self(i,T1) > score_self(i,T2)
```

它学习：

> 对这只股票而言，当前状态是不是一个历史上相对更好的机会。

不需要股票 ID embedding。股票代码只用于训练阶段配对，模型输入仍然只有行情、市场和状态特征，所以新股不存在 OOV 问题。

这种配对还能消除一部分股票自身长期特性，例如：

- 某只股票天然波动更大；
- 某只股票长期流动性较差；
- 不同行业的收益分布不同。

### 3. 不同股票、不同时间

这是最宽泛的约束：

```text
(A,T1) 的未来机会质量 > (B,T2)
→ score_global(A,T1) > score_global(B,T2)
```

它迫使模型学习跨股票、跨市场阶段都可比较的“状态质量”。

但它也是最危险的：如果直接比较未来绝对收益，模型很容易只学会：

- 牛市日期大于熊市日期；
- 高波动年份大于低波动年份；
- 小盘风格周期大于大盘风格周期。

这不一定会增强同日选股。

## 跨日期不能直接比较原始收益

同日 pair 可以直接比较 H7 收益，因为市场环境相同。跨日期 pair 应使用统一尺度，例如：

```text
y_rel(i,t) =
股票 i 的未来 H7 净收益
在 signal_date=t 全市场中的横截面 percentile
```

或者进一步做行业中性：

```text
y_industry_rel(i,t) =
股票未来收益在同日、同行业中的 percentile
```

于是：

- `0.9` 表示该股票未来表现位于当日横截面前 10%；
- `0.2` 表示位于后 20%；
- 不同日期的数据才有相对可比性。

这仍然是 preference learning，不是回归：

```text
y_rel(A,T1) - y_rel(B,T2) > 0.20
→ score_global(A,T1) > score_global(B,T2)
```

模型不需要拟合 `y_rel=0.83`，只需把明显更好的状态排前。

| Head | Pair 来源 | 监督目标 |

| `self_temporal_head` | 同股不同日期 | 当日横截面收益 percentile 排序 |
| `global_temporal_head` | 异股不同日期 | 标准化机会质量排序 |

```text
+ 0.25 × L_drawdown
+ 0.25 × L_self_temporal
+ 0.25 × L_global_temporal
```

第一轮推理时仍然只使用原来的：


> 市场状态的跨日期 preference 可以学到，但绝对分类和跨年份分数校准很难。

## 同股跨时期 Pair 会学到什么

对于同一只股票：

```text
股票 A 在 T1 的未来 H7 收益
vs
股票 A 在 T2 的未来 H7 收益
```

股票长期固有特征大致被控制住：

```text
r(A,T1) - r(A,T2)
≈ market_regime(T1) - market_regime(T2)
 + stock_state(A,T1) - stock_state(A,T2)
```

模型会同时学习：

- 当前整体市场环境是否更有利；
- 这只股票自身当前状态是否更有利；
- 行业周期、动量、波动状态是否改善；
- 同一股票在什么历史状态下更容易赚钱。

当几千只股票都提供这种纵向监督时，它们共同包含的部分，很可能就是市场牛熊和风险偏好。

所以它会比单独使用不到 2,000 个市场日期训练 Market JEV 获得更丰富的监督。

但要注意：

> 只训练同股跨期 Pair，得到的是“股票时机分数”，不保证自动分解成纯市场牛熊分数。

如果直接把所有逻辑塞进一个 scalar，模型仍可能混合市场、行业和个股状态。

## 更优美的结构：显式分解市场与个股

建议模型输出不是一个分数，而是：

```text
market_score(t)       # 日期共享的市场机会
stock_alpha(i,t)      # 股票相对机会

total_score(i,t)
= market_score(t) + stock_alpha(i,t)
```

输入仍然不需要股票 ID：

```text
市场 tokens
→ market_score(t)

股票 tokens + 市场 tokens
→ stock_alpha(i,t)
```

股票代码只在 Dataset 中用于构造“同一股票”的 Pair，不进入模型，因此不会遇到新股 embedding 问题。

最好对 return 和 drawdown 分别进行这种分解：

```text
market_return_score(t)
stock_return_score(i,t)

market_risk_score(t)
stock_risk_score(i,t)
```

## 三类监督如何协同

### 1. 同日异股：保留现有选股能力

```text
(A,t) vs (B,t)
```

训练 `stock_alpha`：

```text
未来 H7 收益 A > B
→ stock_alpha(A,t) > stock_alpha(B,t)
```

因为同一天的 `market_score` 相同，会自然抵消。

### 2. 同股异期：新增时间择时能力

```text
(A,T1) vs (A,T2)
```

训练总分：

```text
未来 H7 收益 T1 > T2
→ total_score(A,T1) > total_score(A,T2)
```

它监督“同一股票何时更值得买”。

### 3. 市场异期：显式锚定牛熊因子

```text
Market(T1) vs Market(T2)
```

直接训练 `market_score`：

```text
未来 H7 全市场中位收益/上涨宽度更高
→ market_score(T1) > market_score(T2)
```

这样才能保证最终抽出的 `market_score` 真正具有市场含义，而不是从股票分数中事后猜测。

第一版暂时不建议加入“异股异期 Pair”。它同时改变股票和日期，容易混入行业、波动率和流动性差异，解释不干净。

Pairwise Head 只学习顺序，raw logit 的绝对零点和尺度没有经济意义，也可能跨年份漂移。

```text
market_rank(T)
```

- 只使用 `T-252 ... T-1`；

   当宽度持续恶化时：

   - 暂停新开仓；
   - 新仓只部署 50%–70%；
   - 不强行清掉已有盈利路径。

3. **分钟级共同风险检测**

   重点不再预测收益，而是检测事件是否正在发生：

   - 个股相关性骤升；

简单讲：

- QMT 是带完整界面的“一体化量化工作站”。
- MiniQMT 是保留行情和交易接口的“轻量执行终端”。

它们通常同属一套迅投系统，MiniQMT 常以“极简模式”或“独立交易模式”存在，并不一定是另一款完全独立的软件。具体名称和权限由券商定制。([docs.thinktrader.net](https://docs.thinktrader.net/QMT-mini/))

| 对比项 | 完整 QMT | MiniQMT |
|---|---|---|
| 使用方式 | 在 QMT 客户端内开发和运行策略 | 外部 Python 通过 `xtquant` 调用 |
| 开发环境 | 内置 Python/编辑器 | VS Code、PyCharm 或独立服务 |
| 回测 | 内置回测和策略管理 | 通常自行使用 QuantX 等外部系统 |
| 图形界面 | 完整行情、研究、策略界面 | 界面很精简 |
| 第三方库 | 受客户端环境约束 | 使用自己的 Python 环境，比较自由 |
| 行情接口 | 客户端内部使用 | `xtdata` |
| 交易接口 | 内置策略接口 | `xttrader` |
| 查询能力 | 通过客户端和内置策略 | 资金、持仓、委托、成交等 API |
| 订单回调 | 内置机制 | 委托、成交、资产和持仓变动回调 |
| 资源占用 | 相对较高 | 相对轻量 |
| 适合场景 | 在一个软件里完成研究到实盘 | 已有研究系统，只需要实盘执行 |
| 运行位置 | Windows 客户端 | MiniQMT 客户端通常仍在 Windows，策略可独立运行 |

MiniQMT 的 `xttrader` 官方接口能够：

- 报单和撤单；
- 查询账户资产；
- 查询持仓；
- 查询委托和成交；
- 获取订单编号、异步请求序号；
- 接收委托、成交、持仓、资产变化等推送。([dict.thinktrader.net](https://dict.thinktrader.net/nativeApi/start_now.html?id=dqamF2))

需要注意，MiniQMT 并非纯云端 API。运行 Python 程序前，仍需要先启动并登录 MiniQMT 客户端；客户端关闭、Windows 休眠或登录失效，交易链路就会中断。([dict.thinktrader.net](https://dict.thinktrader.net/nativeApi/start_now.html?id=dqamF2))

对你这个项目，MiniQMT 更合适：

```text
Linux QuantX
  负责模型、选股、回测和目标持仓
          ↓ HTTP / RPC
Windows 小主机
  MiniQMT + xtquant 交易网关
          ↓
券商账户
```

这样不用把 QuantX、PyTorch、Qlib 等塞进 QMT 内置 Python，只让 Windows 小主机负责：

1. 登录和维持交易连接；
2. 查询资产、持仓、委托和成交；
3. 接收 QuantX 目标持仓；
4. 计算并提交差额订单；
5. 回传订单编号和成交状态；
6. 重启后进行账户对账。

最大的现实差异不是软件功能，而是券商权限：

- 哪些账户能开通；
- 资产门槛；
- 是否同时开放 `xtdata` 与 `xttrader`；
- 是否有模拟账户；
- 支持哪些品种；
- 是否提供 Level-2；
- 是否允许极简模式；
- 程序化交易报备要求。

这些没有全国统一答案，必须向具体券商客户经理确认。不要直接相信网上所谓固定“10 万门槛”；截至 2026 年 9 月，不同券商和营业部差异仍然很大。

就你的需求而言，优先级可以定为：

> 能开 MiniQMT，就用 MiniQMT；只有无法开通时，才退回 EasyTHS 的界面自动化方案。

因为你看到的并不是普通“本地软件调用公开服务器 API”，而是一套受控交易客户端。

真实链路大致是：

```text
自动化程序
  ↓

```

本地客户端只是入口，真正的交易能力和校验都在券商系统。

### 为什么不能简单模拟请求

1. **协议不是公开 API**

每家券商接入同花顺后的登录、查询、报单接口都可能不同。同花顺更像统一外壳，背后连接的是不同券商柜台。

2. **会话并非只有 Cookie**

一般还会涉及：

- 动态会话密钥；
- 设备指纹；
- 客户端版本；
- 心跳和连接序号；
- 短信或图形验证码；
- 委托流水号；
- 时间戳、防重放字段；
- 请求签名和二进制报文。

捕获一次请求，不代表换个时间、价格或数量后还能重放。

3. **加密可能在发送前完成**

即使成功抓到 TLS 流量，看到的也可能只是密文。关键签名由客户端 DLL、券商交易插件或本地加密组件生成，不能靠修改 HTTP 参数完成下单。

4. **请求存在状态机**

下单通常不是单个请求：

```text
登录认证
→ 股东账户初始化
→ 查询交易权限
→ 获取会话/流水号
→ 风控校验
→ 委托提交
→ 委托确认
→ 委托/成交回报
```

缺少中间状态可能被拒单、重复下单，甚至锁定账户。

5. **没有统一协议**

即便成功逆向券商 A，也未必适用于券商 B；客户端升级后偏移、签名或报文格式也可能变化。

6. **合规风险更高**

未经券商认可，直接复刻私有交易协议，很容易被视为未经授权的外部接入。现行规范要求第三方或自行开发客户端经过券商安全评估和正式认可；券商也会监控异常接入行为。([sac.net.cn](https://www.sac.net.cn/zlgl/zlgz/202512/t20251231_69778.html))

### 为什么 GUI 自动化反而常见

GUI 自动化没有伪造交易协议：

```text
程序点击官方客户端
→ 官方客户端负责认证、签名和风控
→ 官方通道报单
```

它技术上笨，但复用了券商认可的完整交易链路。缺点是脆弱，优点是无需逆向几十家券商协议。

### 有没有不走 GUI 的办法？

有三种正规程度不同的路线：

- **券商官方 API**：QMT、MiniQMT、PTrade 等，最好。
- **大 QMT 内置薄执行器**：外部只生成目标仓位，QMT 内部原生下单；更适合你。
- **本地私有协议逆向**：技术上可能做到，但维护和合规风险最高，不建议用于实盘。

所以，不是“不能模拟请求”，而是：

> 可以尝试逆向，但你实际上是在重新实现一个带认证、加密、状态管理和合规约束的券商交易客户端。

对于低频日线策略，为了省掉几百毫秒的 GUI 操作而承担这些风险，不划算。最优解仍是让大 QMT 内部运行一个不包含策略逻辑的薄执行器。
